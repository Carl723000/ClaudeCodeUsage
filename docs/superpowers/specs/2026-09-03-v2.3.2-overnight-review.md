# Claude Code Usage v2.3.2 夜间审阅记录

日期：2026-09-03（Asia/Shanghai）

范围：仅在隔离 worktree `codex/v2.3.1-goal-g0-g6` 内审阅、修复与验证；不推送、不合并、不发布，也不操作远程 issue/PR。

## 本轮结论

### 已复现并修复：Codex 线程标题的路径脱敏边界

Claude CLI 对 `src/providers/codex/codexIdentity.ts` 的标题清洗链路做了定向隐私审计，确认 POSIX 绝对路径在紧贴 ASCII 冒号或部分标点时可能绕过原有正则。例如：

- `3:/Users/carl`
- `3:/etc/passwd`
- `:/etc/passwd`

这些标题只在内存中使用，不会持久化或联网，但可能进入仪表盘和截图，因而仍违反“绝对路径不得展示”的隐私边界。

处理方式：先加入上述三类回归样例，编译后的定向测试按预期失败；随后仅放宽路径前缀识别，不改变标题的其他清洗规则。修复后定向测试 15/15 通过。英文与中文本地数据契约同步补充了“路径紧贴标点也必须脱敏”的要求。

### 已审计、无需修改：Codex 周额度状态栏语义

Claude CLI 复核了状态栏、tooltip 和告警阈值的数据流：

- 紧凑状态栏 `wk 64%` 表示“剩余 64%”，符合本轮产品要求。
- tooltip 的进度条和标签显示“已用百分比”，与 Claude 的明细画风一致。
- 告警颜色按已用百分比判断，避免把“剩余越多”错误视为风险。

这是有测试和变更记录覆盖的刻意语义分工，不是本轮缺陷，因此没有为了表面一致而反转数据。

### 已复现并修复：Claude 图表下钻在 Webview 重载后丢失

Claude CLI 对 Claude/Codex 共用图表交互做定向审计，确认 Claude 的两条既有下钻路径没有进入 Webview 状态：

- “最近 30 天”日柱展开到小时后，刷新/重载会收起。
- “全部时间”月柱展开到每日后，刷新/重载会收起。
- 相同场景下，Codex 的已物化日→小时路径已经能够恢复，形成 provider 间的不一致。

先加入两个真实 Playwright 操作测试，均在完整 `page.reload()` 后检查行可见性、选中态、`aria-expanded` 和延迟详情数据请求。修复前两个测试按预期失败；修复后：

- Claude 日→小时、月→日展开状态写入统一 Webview state，并在重载时恢复。
- 恢复过程会重新请求 Claude 的延迟详情数据，但不自动滚动，之后仍由既有滚动恢复逻辑定位。
- 用户主动切换 tab 时仍按既有规则清空展开状态。
- 控件类型改由控件自身所在 tab 判定，不再依赖初始化瞬间的全局活动 tab；这同时修正了“全部时间”非活动 tab 柱状图初次初始化缺少 ARIA 绑定的边界。

第二次 Claude CLI 只读复核认为当前 diff 没有受支持的阻塞缺陷，并确认 Codex 路径未被改变。它指出的非阻塞测试缺口——恢复后是否重新请求 Claude 的 `getHourlyData` / `getDailyData`——也已加入断言。

### 已复现并修复：分享工作台在五种语言中静默回落英语

三次 Claude CLI 定向审阅先后检查了设置简洁性、本地数据契约和分享工作台的语言覆盖，并通过第二次挑战审阅纠正了首轮的两个误判：

- `CHANGELOG.md` 中“Usage Share Card 默认关闭”的文字位于已发布的 2.2.0 历史区段，记录的是当时行为，不应改写；当前 2.3.1 Unreleased 区段已经正确记录分享工作台默认开启。
- `LocalDataUiCopy` / `renderLocalDataControls()` 虽仍保留为命令动作白名单的源码交叉检查，但已经不接入 `renderSettingsPanel()`；既有 Node 与 Playwright 测试明确锁定“插件设置页不渲染本地数据与隐私控制”。因此它的非英语副本缺口不是活动 UI 缺陷。
- 真正活动的 `CombinedHeatmapUiCopy` 会进入 Compare 分享工作台、客户端预览状态和 SVG 文案；此前只有简体中文、繁体中文和英文完整，德语、日语、韩语、巴西葡萄牙语、印尼语除四个色阶标签外全部回落为英语。

处理方式：先加入从 `CombinedHeatmapUiCopy` 接口推导字段清单的仓库覆盖测试，修复前稳定报告五个缺失 locale；随后补齐五种语言的 34 个活动字段，并在真实 Playwright 渲染中逐一验证八种语言的色阶标签和面板标题。配色名称沿用简繁中文已经采用的规则：保留 Claude、Codex、GitHub 品牌名，翻译颜色形容词。

同时把 `LOCAL-DATA.md` 与 `LOCAL-DATA.zh-CN.md` 中容易让人误以为存在设置面板的“Data 设置提供控制”改为“命令面板提供维护动作”，明确这些动作不进入仪表盘设置页。`enableShareCard = true` 保持不变：这是维护者明确要求的默认行为；现有用户仍可用同一个设置开关隐藏全部分享 UI，导出始终需要显式操作。

### 已审计、暂未复现：Claude 今日 / 最近 30 天数据显示为零

Claude CLI 沿真实生产链路复核了 Claude 的文件发现、增量读取、去重、时区归档、文件监听和 Webview 刷新：

- 顶层会话与嵌套 `subagents/**/*.jsonl` 都由递归发现覆盖；路径键与稳定文件身份共同防止重复计数。
- 新增 CLI 记录可由增量游标读取，`Today` 与最近 30 天汇总最终都使用同一配置时区的自然日键。
- 文件监听事件能够触发重新加载并把新 HTML 发送给现有 Webview。

在当前代码和现有夹具中没有找到能把“昨日、今日均有真实 Claude CLI 使用”稳定变成两个零卡片的生产缺陷，因此本轮没有猜测性修改统计主链。发布前最有价值的补强是加入两个更接近真实磁盘行为的集成测试：一个使用真实嵌套 `subagents/` 目录证明发现且只计一次；另一个由真实 `fs.watch` 事件一路断言到 Webview HTML 更新。它们已记录为后续发布加固项。

后续独立深审仍未推翻这个结论，并按可能性整理了现有机制：历史记录证明 `--no-session-persistence` / `--bare` 会直接造成“CLI 有执行感但无本地 transcript”；`dashboardAutoRefresh=false` 会让非手动触发不推送 Webview，而状态栏仍可更新；窗口失焦会暂停轮询；符号链接项目目录会被安全遍历规则跳过。后三项都是代码中真实存在的机制，但没有证据证明命中维护者当时的环境。本夜所有 Claude CLI 调用都使用标准持久会话，因此新用量已进入本地日志。

### 已复现并修复：配置时区边界下热力图与分享范围偏移

上述审计同时发现两个独立、可确定复现的日期边界问题，第二个 Claude 持久会话继续做了挑战审阅并确认均为活动生产路径：

- Claude provider 自身的 Token 热力图调用 `renderHeatmapSvg(daily)` 时没有传配置时区中的“今天”，会回落到 UTC 日期；在 UTC 前后跨日时可能少一天或多一天。
- Share Card 的 7 天、30 天和一年范围以固定毫秒数过滤，和产品其余部分的“配置时区自然日”口径不一致；UTC 边界附近会把相邻本地日错误纳入或排除。

处理方式：先固定 `Pacific/Honolulu` 与 UTC 跨日样例，证明三个滚动范围都错误纳入相邻旧日，同时用源码契约锁定 provider 热力图缺少配置时区锚点；修复前定向套件 27 通过、2 失败。随后：

- provider 热力图显式以配置时区的当前日作为结束日期；
- 分享范围从固定毫秒阈值改为 7 / 30 / 365 个精确自然日键的集合，并注入可测试的 `now`；
- `today` 与默认当前月也复用同一个 `now`，避免单次计算跨越时钟边界。

修复后定向套件 29/29 通过。挑战审阅还指出 `getUsageAttribution` 的 week/month 仍使用固定毫秒窗口；后续一次独立审计确认了它的活动调用面，并作为下一项边界明确的修复单独落地。

### 已复现并修复：Usage tracking 与 AI advice 的 7 / 30 日归因边界

Claude CLI 对 `ClaudeDataLoader.getUsageAttribution()` 的全部调用点做了独立审计，确认 week/month 仍以 `now - N × 24h` 过滤，而同一函数的 day 分支和刚修正的 Share Card 已使用配置时区自然日。实际受影响的活动界面只有：

- Content 页“Usage tracking”面板的默认 Week 视图及 Week / Month 切换；
- `adviceSummary.ts` 生成 AI advice 输入时的 week 范围。

Claude Today、仪表盘“最近 30 天”、Share Card 和 Codex 聚合均不调用这条函数，因此没有把影响面夸大。`types.ts` 已明确 week = 最近 7 天、month = 最近 30 天；正确口径是“今天 + 前 6 / 29 个配置时区自然日”。

处理方式仍采用红绿测试：分别在 `Asia/Tokyo` 和 `Pacific/Honolulu` 构造 UTC 边界样例，旧逻辑会把第 8 / 31 个本地日纳入，两个测试均稳定失败；随后仅在 `getUsageAttribution()` 内复用 `rollingDayKeysFromDayKey()`，让 day/week/month 共用精确日期键集合，session/project 路径保持原样。

第三次 Claude CLI diff 复核没有发现阻塞问题，但指出 `ContentAnalysis.skillUses[].day` 是解析时缓存值：用户改时区而文件未变化时，增量索引不会重新解析，旧 day 可能滞留。为避免只修 record 而遗漏 skill/plugin 归因，又增加一个先红后绿样例，并在过滤时优先由绝对时间 `ts` 按当前配置时区重新归档；只有不可解析的旧记录才回退缓存 day。最终定向 `dataLoader` 套件 16/16 通过。

同一复核还确认浏览器侧 `applySessionFilters()` 仍用宿主系统午夜和固定毫秒窗口筛 Content session 列表；这是不同代码层的独立缺陷，已留作下一轮测试驱动修复，不混入本提交。
