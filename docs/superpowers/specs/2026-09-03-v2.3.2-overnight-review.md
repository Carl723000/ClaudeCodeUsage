### 已复现并修复：Codex 线程标题的路径脱敏边界

Claude CLI 对 `src/providers/codex/codexIdentity.ts` 的标题清洗链路做了定向隐私审计，确认 POSIX 绝对路径在紧贴 ASCII 冒号或部分标点时可能绕过原有正则。例如：

- `3:/etc/passwd`

这些标题只在内存中使用，不会持久化或联网，但可能进入仪表盘和截图，因而仍违反“绝对路径不得展示”的隐私边界。

处理方式：先加入上述三类回归样例，编译后的定向测试按预期失败；随后仅放宽路径前缀识别，不改变标题的其他清洗规则。修复后定向测试 15/15 通过。英文与中文本地数据契约同步补充了“路径紧贴标点也必须脱敏”的要求。

### 已审计、暂未复现：Claude 今日 / 最近 30 天数据显示为零

Claude CLI 沿真实生产链路复核了 Claude 的文件发现、增量读取、去重、时区归档、文件监听和 Webview 刷新：

- 顶层会话与嵌套 `subagents/**/*.jsonl` 都由递归发现覆盖；路径键与稳定文件身份共同防止重复计数。
- 新增 CLI 记录可由增量游标读取，`Today` 与最近 30 天汇总最终都使用同一配置时区的自然日键。
- 文件监听事件能够触发重新加载并把新 HTML 发送给现有 Webview。

在当前代码和现有夹具中没有找到能把“昨日、今日均有真实 Claude CLI 使用”稳定变成两个零卡片的生产缺陷，因此本轮没有猜测性修改统计主链。后续已补入两项更接近生产路径的回归：第一项在真实临时目录创建顶层 transcript 与嵌套 `session/subagents/agent-*.jsonl`，证明冷索引会把两者分别计入 Today、最近 30 天、全部时间和 Sessions，未变化刷新零 body read，subagent 追加只读该文件尾部且不会重复累计；第二项直接驱动生产 `startFileWatching()` 注册的递归 watcher callback，证明嵌套 subagent `.jsonl` 会触发一次 `watch` refresh，而相邻 `.meta.json` 不会误触发。

这两项测试均在旧代码上通过，因此进一步缩小了嫌疑范围，但仍没有复现维护者截图中的零值。第二项使用受控 watcher callback，不把它夸大为真实操作系统 `fs.watch` 一路到 Webview HTML 的端到端测试；该完整链路以及多候选 Claude data root 的自动选择仍是最有价值的后续诊断。

后续独立深审仍未推翻这个结论，并按可能性整理了现有机制：历史记录证明 `--no-session-persistence` / `--bare` 会直接造成“CLI 有执行感但无本地 transcript”；`dashboardAutoRefresh=false` 会让非手动触发不推送 Webview，而状态栏仍可更新；窗口失焦会暂停轮询；符号链接项目目录会被安全遍历规则跳过。后三项都是代码中真实存在的机制，但没有证据证明命中维护者当时的环境。本夜所有 Claude CLI 调用都使用标准持久会话，因此新用量已进入本地日志。

### 已复现并修复：Claude 文件监听的异步错误没有安全降级

为补齐上一节留下的真实 `fs.watch` 缺口，本轮加入了从临时 Claude transcript、操作系统文件事件、manifest diff、增量索引到 Webview `updateData()` 的整链测试。受限测试宿主在注册递归 watcher 后异步返回 `EMFILE`；这暴露出一个独立的生产缺陷：原实现的 `try/catch` 只能捕获 `fs.watch()` 同步抛错，没有监听 `FSWatcher` 后续发出的 `error` 事件，因而资源耗尽或文件系统 watcher 故障可能逃逸到 Extension Host。

处理方式先以独立红灯锁定：watcher 注册后必须存在异步错误处理，错误发生后要关闭真实 watcher、释放 ownership lease、清空当前监听目录，并保留轮询作为降级路径。修复只记录安全的错误码，不记录本地路径或文件名。随后保留整链测试：支持递归 watcher 的宿主会验证新增嵌套 subagent 文件把 Today 从 10 更新到 30，同时 manifest 与记录数都变为 2；无法分配 watcher 的受限宿主会明确跳过该能力测试，而专门的错误路径测试仍必须通过。

该修复提高了实时刷新失败时的稳定性，但轮询本来就是后备路径，因此不能据此断言维护者截图中的 Claude Today / 最近 30 天零值已经被复现或完全解决。当前机器只检测到一个有效默认 Claude data root，且其最新 `.jsonl` 修改时间为 2026-09-03 06:16 CST；没有发现 `CLAUDE_CONFIG_DIR` 覆盖或第二个候选根目录，因此“误选旧 profile”在本机没有证据支持。

### 已复现并修复：配置时区边界下热力图与分享范围偏移

上述审计同时发现两个独立、可确定复现的日期边界问题，第二个 Claude 持久会话继续做了挑战审阅并确认均为活动生产路径：

- Claude provider 自身的 Token 热力图调用 `renderHeatmapSvg(daily)` 时没有传配置时区中的“今天”，会回落到 UTC 日期；在 UTC 前后跨日时可能少一天或多一天。
- Share Card 的 7 天、30 天和一年范围以固定毫秒数过滤，和产品其余部分的“配置时区自然日”口径不一致；UTC 边界附近会把相邻本地日错误纳入或排除。

处理方式：先固定 `Pacific/Honolulu` 与 UTC 跨日样例，证明三个滚动范围都错误纳入相邻旧日，同时用源码契约锁定 provider 热力图缺少配置时区锚点；修复前定向套件 27 通过、2 失败。随后：

- provider 热力图显式以配置时区的当前日作为结束日期；
- 分享范围从固定毫秒阈值改为 7 / 30 / 365 个精确自然日键的集合，并注入可测试的 `now`；
- `today` 与默认当前月也复用同一个 `now`，避免单次计算跨越时钟边界。

修复后定向套件 29/29 通过。挑战审阅还指出 `getUsageAttribution` 的 week/month 仍使用固定毫秒窗口；后续一次独立审计确认了它的活动调用面，并作为下一项边界明确的修复单独落地。

### 已复现并修复：Usage tracking 与 AI advice 的 7 / 30 日归因边界

Claude CLI 对 `ClaudeDataLoader.getUsageAttribution()` 的全部调用点做了独立审计，确认 week/month 仍以 `now - N × 24h` 过滤，而同一函数的 day 分支和刚修正的 Share Card 已使用配置时区自然日。实际受影响的活动界面只有：

- Content 页“Usage tracking”面板的默认 Week 视图及 Week / Month 切换；
- `adviceSummary.ts` 生成 AI advice 输入时的 week 范围。

Claude Today、仪表盘“最近 30 天”、Share Card 和 Codex 聚合均不调用这条函数，因此没有把影响面夸大。`types.ts` 已明确 week = 最近 7 天、month = 最近 30 天；正确口径是“今天 + 前 6 / 29 个配置时区自然日”。

处理方式仍采用红绿测试：分别在 `Asia/Tokyo` 和 `Pacific/Honolulu` 构造 UTC 边界样例，旧逻辑会把第 8 / 31 个本地日纳入，两个测试均稳定失败；随后仅在 `getUsageAttribution()` 内复用 `rollingDayKeysFromDayKey()`，让 day/week/month 共用精确日期键集合，session/project 路径保持原样。

第三次 Claude CLI diff 复核没有发现阻塞问题，但指出 `ContentAnalysis.skillUses[].day` 是解析时缓存值：用户改时区而文件未变化时，增量索引不会重新解析，旧 day 可能滞留。为避免只修 record 而遗漏 skill/plugin 归因，又增加一个先红后绿样例，并在过滤时优先由绝对时间 `ts` 按当前配置时区重新归档；只有不可解析的旧记录才回退缓存 day。最终定向 `dataLoader` 套件 16/16 通过。

同一复核还确认浏览器侧 `applySessionFilters()` 仍用宿主系统午夜和固定毫秒窗口筛 Sessions 列表；这是不同代码层的独立缺陷，随后作为下一项边界明确的修复单独落地。

### 已复现并修复：Claude / Codex Sessions 使用宿主时区过滤

Claude CLI 对浏览器侧 `applySessionFilters()` 做了独立调用面审计，确认旧实现以 Webview 所在机器的本地午夜处理 `today`，并以 `Date.now() - N × 24h` 处理 7 / 30 天。实际影响面是 Claude Sessions 的 Today / 7 / 30 天，以及 Codex Sessions 的 7 / 30 天；Workflows 和 Compare 不经过这条路径。

UTC 边界反例可以稳定复现错误：当 Webview 运行在香港时区、插件配置为 `Pacific/Honolulu`，Honolulu 当日凌晨的 session 会被 Today 隐藏；7 / 30 天还会错误纳入边界外的相邻本地日。相反方向在 `Asia/Tokyo` 也可能把配置时区的昨日保留在 Today。

处理方式仍采用红绿测试：先在 Playwright 中固定浏览器时钟和 Honolulu 配置时区，旧实现稳定把 `Honolulu today` 隐藏；随后由服务端为 Claude 与 Codex session 主行写入配置时区的 `data-day-key`，客户端以插件宿主解析后的配置时区构造“今天 + 前 6 / 29 日”的精确自然日集合。这样也覆盖空值表示“系统时区”以及远程插件宿主和本地 Webview 时区不同的情况。过滤状态在完整 Webview 重载后继续保留，明细行仍跟随主行显隐。

修复后定向 Playwright 1/1 通过，完整 UI 回归 122/122 通过。第三个 Claude CLI diff 复核在达到回合上限前完成了源码编译、生成脚本正则、服务端日期键和定向绿灯检查，未报告已证实缺陷；由于没有生成最终结论，本记录不把它表述为完整验收。它另行指出 Claude `formatDateTime()` 仍使用宿主时区 getter，这是显示层的独立后续项，不与本次范围过滤修复混在一起。

### 已复现并修复：Claude 列表时间标签忽略配置时区

新一轮 Claude CLI 只读审计确认 `UsageWebviewProvider.formatDateTime()` 完全依赖 Extension Host 的 `Date#getHours/getDate/getMonth/getFullYear`，未读取 `I18n.getTimezone()`。它只影响 Claude 分支，但调用面横跨 Sessions、Projects、Branches 和 Workflows 的七处时间列；Codex 同类标签已经通过 `createCodexLocalizedFormatters()` 使用配置时区。

最直接的矛盾位于同一个 Claude Session 行：过滤用的 `data-day-key` 已按配置时区生成，紧邻的可见日期文本却按宿主时区显示。在宿主为 UTC、配置为 `Asia/Tokyo`、当前时刻为 `2026-09-03T15:00:00Z` 时，`2026-09-03T14:00:00Z` 的 session 旧逻辑显示为 `Today 14:00`，而配置时区中的正确含义是 `Yesterday 23:00`。

处理方式：先加入 Today/Yesterday、DST 切换和跨年分支三个定向测试，旧实现实际结果为 1 通过、2 失败；随后把方法改为使用解析后的配置时区、`dayKeyInZone()` 和自然日键计算 Today/Yesterday，并用明确的 `h23` 时钟格式保持原有 `HH:MM` 外观。DST 的“昨日”由日期键运算得到，不以 24 小时毫秒相减。挑战复核后又补上同年紧凑格式、无效/epoch sentinel，以及八种 UI locale 的 Today/Yesterday 文案覆盖，最终定向测试 5/5 通过。

同一持久 Claude 会话对 diff 给出 `ACCEPT`，确认配置时区、DST、24 小时制、八语言文案和 Extension Host / Webview 边界均未发现阻塞缺陷。需要披露的是：Claude 在明确的只读要求下误执行了一次 `git stash`，随即 `pop` 恢复；本地随后逐文件核对 diff、未跟踪测试、stash 列表和完整回归，确认没有丢失或混入变更。审阅还确认三个相邻但独立的既有问题仍待后续处理：Workflow“本月”聚合、图表 tooltip 日期和 Advice snooze 日期仍有宿主时区路径。

第三次 Claude CLI 独立复核被限制为只读搜索工具，没有再获得 Git 或写入能力。它未发现正确性阻塞项，但指出初版修复在每个表格行会重复构造 6 个 `Intl.DateTimeFormat`，与 Codex 一次创建、整表复用的既有模式不一致。新增构造次数回归后，旧修复对两个标签实际构造 12 次（预期 2 次），稳定红灯；随后在 Webview provider 内按配置时区缓存一个同时产出日期键和 `HH:MM` 的 formatter，并让 Session 的过滤日期键复用它。最终两个标签合计只构造 2 次，后续行不再新增 formatter，同时保持全部语义测试不变。

### 已复现并修复：Workflows 摘要混用自然月与滚动 30 天

Claude CLI 对 Workflows 页摘要及其数据入口做了只读审计，确认旧实现把分子按 Extension Host 的自然月和 `endTime` 筛选，而分母 `this.monthData` 实际来自 `materialized.last30Days`。因此它不仅会在 UTC 边界错分，还会在每次渲染中把“自然月工作流成本”除以“滚动 30 天总成本”，页面上的“本月”文字也与中间仪表板标签的真实口径冲突。

同一持久 Claude 会话继续查阅 CHANGELOG、既有滚动范围测试和调用点后给出高置信度结论：Workflows 摘要应与中间页保持一致，范围是配置时区中的“今天 + 前 29 个自然日”；工作流按列表展示和排序所采用的 `startTime` 归属，而不是可能跨日或跨月的 `endTime`。不应为此新增自然月数据管线，也不应改动状态栏中确实仍采用自然月的月成本选项。

处理方式仍采用红绿测试：在 `Asia/Tokyo` 下固定当前时刻，把两个工作流开始时间放在 30 日边界的前后一分钟，并故意让结束时间跨入范围。旧实现实际显示 `Workflows this month: 2 · $30.00 · 75%`，稳定证明了错误；修复后只纳入边界内开始的一个工作流，显示 `1 · $10.00 · 25%`，与同一滚动 30 天分母核对。摘要使用既有自然日键工具并复用缓存的配置时区 formatter；八种 UI locale 的“最近 30 天工作流 / 成本占比”文案也由独立断言覆盖。

### 已复现并修复：图表日期标签受宿主时区影响

Claude CLI 对 `src/webview.ts` 的浏览器侧日期格式化调用做了只读审计，确认已经按配置时区归档的 `YYYY-MM-DD` / `YYYY-MM` 用量键，在若干活动路径中又被 `new Date(key)` 解析成 UTC 午夜，再按 Webview 宿主或配置时区显示。受影响的活动路径包括主图切换指标后的 tooltip / ARIA 标签、日→小时标题、月→日标题、每日 Token 构成标签和每日明细表日期。宿主位于 UTC 以西时，日键会退回前一天；月键会退回前一个月。该问题与数据归档无关，属于显示层二次解析错误。

处理方式仍采用红绿测试：先让 Playwright 在 `America/Los_Angeles` 宿主时区切换日/月主图指标，并在插件配置为 `Pacific/Honolulu` 时直接渲染日、月下钻。旧实现稳定把 `2026-07-20` 显示为 `7/19/2026`，把 `2026-07` 显示为 `June 2026`，每日构成与表格中的 `7/1` 也都退成 `6/30`。随后在 Webview 客户端加入一个只处理规范用量键的 formatter：按组件解析，使用 UTC 正午 sentinel，并固定以 UTC 输出既有 locale 格式，从而不再让宿主或配置时区对已经归档的键做第二次位移。

绿灯过程中又捕获到服务端共享 helper 的相邻缺陷：`formatUsageDate('2026-07', ..., true)` 会把缺失的日组件传入 `Date.UTC()`，得到 `Invalid Date`。增加独立红灯后，月键明确以每月 1 日的 UTC 正午 sentinel 格式化。最终定向 Node 3/3、Playwright 2/2、完整 Node 920 通过（另 1 项跳过）、完整 Playwright 124/124 通过。

### 已复现并修复：Advice / Optimizer 暂停日期使用宿主时区

上一轮审计留下的五个活动显示调用都直接执行 `new Date(snoozedUntil).toLocaleDateString()`，没有传入 UI locale 或插件配置时区。暂停是否到期本身按 epoch 毫秒比较，是刻意的七天持续时间语义，不受时区影响；错误只发生在用户看到的截止日期。Extension Host 与配置时区分居日期边界两侧时，页面会把同一个截止时刻显示成不同自然日。

处理方式：在 Node 测试中把宿主固定为 UTC、插件配置为 `Pacific/Honolulu`，并把截止时刻固定为 `2099-01-01T00:30:00Z`。旧实现显示 `Snoozed until 1/1/2099`，而配置时区中的正确日期是 `12/31/2098`。随后增加一个仅负责 Advice 暂停日期的 formatter，复用 `I18n.getLocale()` 与 `I18n.dateFormatOptions()`，并让 Advice 活动卡、折叠摘要和 Optimizer 两种暂停状态共用它；到期判定与七天时长完全不变。

修复后定向测试 9/9、完整 Node 921 通过（另 1 项跳过）、完整 Playwright 124/124 通过。本轮原计划再次调用 Claude CLI 审计这两条剩余路径，但权限审阅器在 CLI 启动前拒绝了仓库源码传输；遵守限制后只使用本地搜索、测试和实现，没有尝试绕过，也没有新增 Claude usage。
