# v2.5.3 Project-scoped AI usage review plan

Status: planning frozen; implementation is not authorized.
Target train: internal `v2.5.3` slot within `v2.5.x`; it need not ship as a standalone Marketplace release.
Product host: the existing `Explore → Projects` surface; no new top-level tab.
Prerequisites: the v2.3.1 safe AI request boundary and local-data controls, the X-06 project-usage matrix, and the v2.4.x recommendation-experiment/comparable-task envelope.

## 1. Placement decision

This feature does not reopen v2.3.1 and does not block its install verification or release decision. It is more sensitive than ordinary project aggregation: it may read selected project input/output text, invoke a user-selected remote AI or local Claude CLI, and retain a structured recommendation result. It therefore belongs to the `v2.5.x` “local efficiency lab”, with `v2.5.3` as its candidate internal slot.

It does not depend on GitHub Connect. It may share a package with other v2.5.x capabilities, but its consent, clearing, network, and rollback boundaries remain independent.

## 2. User outcome

After selecting one project, provider, and date range, the user first receives a deterministic, fully local usage-behavior summary and then decides whether to invoke AI for deeper review. The report answers:

- how tokens, caching, context, model/effort, sessions, and iteration behavior changed in this project;
- which input/output patterns may indicate repeated work, context growth, or redundant review;
- one small experiment to try on the next comparable task; and
- which observable metric should be used to evaluate that experiment.

The report must not infer productivity, code quality, research quality, individual performance, or model capability from token volume alone.

## 3. Three review modes

1. **Local usage review (default):** numeric and structural aggregates from existing indexes only; no network and no content reads.
2. **AI aggregate review:** sends a user-previewed and confirmed project aggregate snapshot; no prompt, response, path, project name, thread title, or account identifier.
3. **AI content-assisted review (separate consent):** reads only the conversations/date range selected for this run and produces bounded, sanitized input/output samples. Before sending, the UI shows the exact items, roles, byte count, and final request body; the user can remove any item. Aggregate-review consent never implies content consent.

No mode may automatically scan the workspace, source code, dotfiles, secrets, git remotes, terminal history, or unselected conversations.

## 4. Analysis semantics

### 4.1 Deterministic local evidence

- provider-native processed, fresh-input, cached-input, output, and reasoning semantics;
- cache reuse/warm-up, context churn/compaction, and long-context growth;
- model and reasoning-effort changes across task phases;
- structural counts for session splits, resumes, subagents, and tool steps;
- observable proxies for retries, repeated review, unchanged long chains, and output rewrites;
- input/output length, turn count, and ratios; and
- separate columns for official quota observations, API-equivalent value, and local tokens—never substitutes for one another.

### 4.2 AI interpretation layer

Every finding uses a fixed structure:

`observation → local evidence reference → why it may matter → one next experiment → measurement → confidence/limits`

AI may only interpret the frozen snapshot. It cannot rewrite source metrics, change model/effort, edit project files, run commands, or perform external writes. Content-assisted mode may discuss prompt structure, output verbosity, or repeated instructions, but must not equate writing style with task quality.

## 5. Local and outbound data-contract delta

| Data class | Content | Persistence | Outbound rule |
|---|---|---|---|
| Project review snapshot | Anonymous `projectRef`, provider, date/timezone, coverage, model/effort, token and structural aggregates, evidence IDs | Generated on demand by default; no second log index or permanent per-project cache | Sent only in AI aggregate/content modes after exact preview |
| Optional content samples | Inputs/outputs selected for this run, roles, local order, sanitation flags | Memory only until completion/cancellation; never globalState, logs, or reports | Separate consent and itemized preview; stop at item/byte limits without silent truncation |
| Request preview | Backend, model, mode, exact body, byte count, snapshot hash | Not persisted by default; only value-free audit metadata may be retained | Preview and actual body must be byte-identical |
| Structured review result | Finding IDs, evidence IDs, confidence, limitations, experiment, measurement | Optional local save; schemaVersion, bounded count/retention, per-item/all clear; no raw quotes or raw CLI output | Not sent again by default |
| Consent/preferences | Default mode, retention choice, last backend | Bounded local settings; content consent is per request and cannot be “always allow” | Never outbound |
| AI credential | Existing SecretStorage key or a future separately reviewed secret key | SecretStorage only | Used only for the confirmed backend; never body, preview, or Webview state |
| CLI audit metadata | Sanitized executable identity, version, model, input hash, time, exit status | Optional bounded record; no raw stdout/stderr | Never sent to a second service |

`projectRef` is a one-way derivation from machine salt and the provider-native project key. The runtime UI may show the local project name, but persisted results and outbound payloads must not contain that name or an absolute path.

## 6. AI backend boundaries

### 6.1 Existing BYOK/API mode

- Reuse the v2.3.1 preview → separate Send → result flow, timeouts, cancellation, and SecretStorage.
- Endpoint/model/key failures exit safely; disabled mode has zero requests and zero timers.
- Send only the exact previewed payload, with no diagnostics, paths, or ambient context.

### 6.2 Optional local Claude CLI mode

This adapter is an independent v2.5.3 safety gate. Finding `claude` on the machine never enables it automatically:

- show the exact executable, version, model, mode, payload bytes, and network disclosure for every run;
- spawn an argument array directly and stream stdin—never concatenate a shell command; use print mode, no tools, no session persistence, safe mode, an isolated empty cwd, a minimal environment, timeout, and cancellation;
- grant no repository tools, project cwd access, MCP, plugins, or hooks; treat all project input/output as untrusted data;
- cap captured output, validate it against the schema before display, and never persist raw stdout/stderr; and
- on expired login, quota exhaustion, timeout, or non-zero exit, offer at most one explicit retry and never loop in the background.

The local CLI may still send the confirmed payload to its AI service, so the UI must not call it “fully offline”.

## 7. Prompt injection and output validation

- Project input/output, tool results, code fragments, and earlier model replies are **untrusted data**; embedded instructions cannot alter the reviewer system contract.
- The reviewer has no tools, network tools, or write access and returns versioned JSON only.
- The output schema includes at least `schemaVersion`, `snapshotHash`, `scope`, `findings[]`, and `limitations[]`; every finding references evidence IDs present in the request.
- Unknown evidence, cross-project claims, unsupported quality claims, invented causality, and auto-execution advice invalidate the finding. Parse failure is shown as failure and never falls back to unvalidated free text.
- The renderer uses `textContent` or an equivalent safe renderer; model HTML/Markdown never becomes executable DOM.

## 8. UI and interaction placement

Add a “Generate AI usage review” action to the selected project detail within `Explore → Projects`:

1. choose provider, project, and a 7/30/90-day or custom range;
2. inspect the local deterministic summary and coverage;
3. select one of the three modes;
4. inspect and edit the exact payload preview;
5. explicitly Send/Run, with cancellation; and
6. read results as observation–evidence–experiment–measurement, then optionally save the sanitized result, mark the experiment tried, or clear it.

Single-provider, no-content, insufficient-sample, rebuilding-data, and AI-unavailable states all need explicit empty states. Reload restores only nonsensitive choices and never restores an unsent body or automatically resends it.

## 10. Acceptance matrix

- [ ] The selected project never mixes a same-named project, another provider/profile, or another date range.
- [ ] Local mode has zero network and zero content reads; closing the page leaves no timer/watcher/worker.
- [ ] Warm unchanged reuses the existing snapshot and does not rescan JSONL.
- [ ] Aggregate-only payload has no project name, path, account, thread/session ID, prompt/response, or unknown field.
- [ ] Content mode requires per-run consent; exact preview equals the body; cancellation sends nothing.
- [ ] Secret/path/project/privacy canaries cannot leak through API, CLI, result persistence, or export.
- [ ] Malicious input/output cannot obtain tools, alter the system contract, execute HTML, or fabricate evidence.
- [ ] Findings with missing evidence are rejected; insufficient samples yield “insufficient evidence” rather than generic advice.
- [ ] Tokens, cost, quota, forecast, and quality proxies are separate and carry coverage/confidence.
- [ ] Timeout, cancellation, expired CLI login, exhausted quota, non-zero exit, oversized output, and malformed JSON fail closed.
- [ ] Raw content, full requests, and raw CLI output are not persisted; structured reports obey bounded retention and exact clearing.
- [ ] Migration, window reload, repeat clicks, and stale ACKs do not duplicate calls or revive cleared data.
- [ ] All copy covers eight locales; keyboard/focus/ARIA, light/dark themes, and approximately 360 px pass.
- [ ] Docs state that local CLI is not necessarily offline, AI advice is not a productivity/quality judgment, and the extension never auto-executes advice.
- [ ] Before a real release, Codex runs the complete gate and Claude performs bounded read-only reviews of the spec, payload/security diff, advice semantics, and final candidate.

## 11. Explicit non-goals

- No project/person productivity score, leaderboard, cross-user benchmark, or “which model is strongest” claim.
- No automatic edits to model, effort, prompts, code, CLAUDE.md, settings, issues, or pull requests.
- No background AI calls, quota-triggered sending, or permanent consent inherited from one run.
- No retained full-project conversation corpus and no second raw prompt/response index.
- No GitHub connection, sync, public sharing, or community data prerequisite.

## 12. Conditions to start the next Goal

Create an implementation Goal only after all of the following are true:

1. v2.3.1 has completed the maintainer's install test and has a release-or-revise decision;
2. the X-06 project-usage matrix is on a stable line or its snapshot contract is frozen;
3. the v2.4.x comparison envelope and local feedback/clear semantics are reusable;
4. the user decides whether this run ends at R4 or also authorizes the R5 local Claude CLI safety gate; and
5. the data contract, README/LOCAL-DATA, and clear inventory are planned to ship with the code change.
